# train_bpe 预分词并行化

## 2026-11-03

### 问题是什么

把 BPE 训练里最重的预分词和词频统计并行化之后：协议怎么设计、`start()` 失败和运行期崩溃分别会怎样、要不要用活着的 worker 凑合跑、失败时怎么退出才不留孤儿进程、要不要边投任务边收结果、崩溃发现得慢和不做错误恢复算不算没做完。

### 现象/尝试

Profiling 时 `count_words` 占大头，merge 必须等全局词频，所以只并行「按块计数」，合并仍在父进程串行做。切 128 块、开 8 个 worker，任务进共享队列，谁空谁拿，不是一块一个进程。

一开始启动循环没有收尾：第 5 个 `start()` 抛错时前 4 个已经在空队列上 `get`，后面的投递、收取、`join` 都不会跑。运行期崩溃则更安静：父进程还在等固定数量的结束标记，缺一个就堵在 `get` 上。后来在超时里查退出码、再在启动失败和崩溃两处各写一份停进程，最后收成外层一份共享回收。

还讨论过：任务全部投完再收结果，大 `Counter` 会不会把队列管道堵住；要不要另开线程同时消费；崩溃后要不要用剩下的 worker 接着跑、要不要重放丢失的那一块。

### 讨论结论

**设计理念：只并行可独立的计数，合并仍要全局**

一块文本的预分词和局部词频不依赖别的块。pair 频率和选下一次 merge 依赖全语料，所以 worker 只返回每块的词频表，父进程加总后再建 pair 表、再串行 merge。切块对齐 special，避免把分隔符劈开；块内仍按全部 special 切开，special 段本身不计入词频。没有传入 special 时，切块仍用 `<|endoftext|>` 的字节形式，以满足切块函数「必须是 bytes」的约定。

**协议：共享队列 + 结束标记，结束条件绑在 worker 数上**

父进程先投完全部块，再按 worker 数投放结束标记，然后收结果。worker 循环取任务，碰到结束标记就往结果队列回投一个结束标记并退出。父进程等到收齐与 worker 数相同的结束标记，再 `join`。因此「全部完成」的含义是「每个 worker 都正常收工」，不是「块数到齐」。快乐路径下块先于结束标记入队，活着的 worker 会把块做完再收工。

**失败约定：不降级、不续跑，这一趟作废**

`start()` 中途失败不接着用已经拉起的那几个。结束标记数量写死在计划的 worker 数上，少人跑却仍按原人数等待，会少结束标记而卡死；改人数等于另做一套协议。`start()` 失败往往是资源不够，剩下的也不一定稳，静默少人还会让人误以为还是满并行。

运行期崩掉的 worker 已经把「正在做的那一块」从队列里拿走且没送回结果，别人补不了。merge 不能在缺块的词频上做。所以失败即整次训练失败。丢掉的是这一趟内存里的部分计数，不是磁盘上的语料；恢复办法是重新跑，不是半截续训。带身份的重试队列超出作业范围。

**退出：检测和收尾分开，收尾共享**

`start()` 失败会立刻在父进程抛错，但抛错本身不会停掉已经拉起的子进程。运行期崩溃则不会惊动父进程，要自己看退出码。子进程默认非 daemon：父进程异常后解释器会 `join` 它们，堵在空队列上的活进程会让退出卡死；pytest 接住异常时父进程甚至还不退出，worker 会留下来。

安全退出的顺序是：确认失败 → 对还活着的发终止 → 对已经有 pid 的 `join`（没启动成功的不要 `join`）→ 再让异常离开。检测可以有多处（启动失败、超时里看到非零退出码），停进程只应有一份，挂在「有进程之后、异常离开这段区域」上，而不是每种错误抄一遍。成功路径只 `join`、不终止。

内层可以把启动失败、崩溃改写成更清楚的说明；外层回收之后应把当前异常继续抛出，不要再包一层空的运行时错误。`except` 里继续抛出时不要再拿变量扔一次，否则回溯容易停在回收那一行。外层接的是普通异常，中断信号仍可能绕过回收；作业可接受。

**发现崩溃是轮询，不是事件**

看退出码的时机是结果队列空、收取超时。别人还在往结果队列塞表时，父进程不会去看谁死了。子进程一死操作系统就有退出码，父进程最多在「结果断流后的下一次超时」才看见。把超时改短或每次收到结果也扫一眼，仍是轮询。训练时间在计数和 merge 上，不在这点检测延迟上。

活着但卡住（忘了结束标记、堵在读文件）和已经非零退出不是一回事：前者退出码仍空，看起来像正在算一块很大的数据。靠心跳或整段超时才能区分，容易误杀。作业不判断卡住。

**不必同时消费**

先投完再收取，任务对象很小。结果表很大时 worker 可能堵在投放上，等父进程开始收取就会松开。真要边投任务边收结果，父进程得另有人在收，多一条线程的生命周期比管道满更麻烦。队列内部的写管道线程不能替代父进程及时收取。作业保持两阶段即可。

**和启动失败不是一类问题**

启动失败：有的子进程根本没诞生。队列堵住：进程都活着，只是管道满了。崩溃：已经启动的进程非零退出。三种都可能看起来像「挂了」，处理不同。

### 设计理念（对照当前实现）

- 固定 8 个 worker、128 块，共享任务队列，块结果是局部词频，父进程加总。
- 结束标记在任务队列和结果队列成对出现，等待人数等于计划的 worker 数。
- 有进程的区域用同一份失败回收；启动失败只负责改写说明，崩溃只在超时空闲时检查退出码。
- 切块标记与词表里 special 的编码方式一致（UTF-8 字节）。
- 块解码允许忽略非法 UTF-8，与课程示例一致，跨块劈开多字节字符时可能丢掉边角字节，可接受。
- 单字节 `bytes` 对象预先固定一份，避免计数时反复分配。

### 遗留卡点

并行计数的失败出口按作业要求已经收拢。不做：卡住检测、崩溃后重放丢失块、事件驱动的立刻发现、用更少 worker 降级跑。`train_bpe` 本身是否正确、是否够快，仍靠官方测试和完整语料训练验证，与这篇生命周期讨论分开。
